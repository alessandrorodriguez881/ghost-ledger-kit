The problem, from the recordings: asked If nothing changes, what will this cost me in total five years from now?, llama3.2:3b wrote 539.40 (5 x 107.88, right arithmetic) and the number guard rejected it because 539.40 is in no row; another time it assumed a 5% interest rate found nowhere and built 617.51. Today the guard can only reject. The new behaviour: the model never does arithmetic; it names the calculation, and the kit does it from the alert fields, so a correct total becomes possible and an invented assumption still cannot get in.

1. Prompt (ledger_kit/explainer.py, _call_llm): add to the system prompt: when the question needs arithmetic (a total over several periods, a sum, a difference, a share), do not compute it; write it as a placeholder [[calc: EXPRESSION]], where EXPRESSION uses only the names of numeric fields of the alert as given in the Alert JSON, the operators + - * / and parentheses, and whole numbers that appear in the user's question (in digits or words); the kit computes it. Keep every existing rule of the prompt.

2. New module ledger_kit/calc.py: find every placeholder in the answer; parse EXPRESSION with a whitelist parser (Python ast is fine: only BinOp with Add, Sub, Mult, Div, UnaryOp minus, Name, and integer Constant; nothing else, no calls, no attributes, no powers); a Name must be a numeric field of this alert (Decimal); a constant must be a whole number found in the question text, in digits or English or Spanish words (reuse ledger_kit/number_words.py); compute in Decimal, round money to 2 places half-up; division by zero, an unknown name, a constant not in the question or a disallowed node rejects the whole answer (fallback, with a reason recorded the way rejected tokens and price_index_as_cause are recorded, for example calc_not_allowed with the offending part). The result replaces the placeholder in the text, written in the same style as the alert amounts (currency included), and the kit records each calculation: the expression, each operand with its field name and value, and the result.

3. Guard order: the number guard runs on the answer with every valid placeholder replaced by a neutral marker, so figures the model wrote itself are still checked exactly as today, and computed results are not checked against the rows because the kit made them from listed fields. Then the index-as-cause check, then the substitution. An answer that writes a computed figure by hand (no placeholder) is still rejected as today.

4. Display: wherever an accepted LLM answer is shown (alert cards, the Provoke the LLM panel, the replay), a computed figure is marked and followed by one line in small text, for example computed by the kit: yearly_cost 107.88 x 5 = 539.40, from the alert fields. Add the computed figures to the explanation result so the UI can show them (a new field on Explanation with a default, so nothing else breaks).

5. Tests (mock client only; no network): the 539.40 case with [[calc: yearly_cost * 5]] and the question with five in words is accepted and shows 539.40 with its provenance line; the same with 5 written by hand as 539.40 is rejected as today; [[calc: yearly_cost * 1.05]] is rejected (1.05 is not in the question); an unknown field, a power, a function call and a division by zero are rejected; Spanish question words work (cinco años); Hypothesis property: any expression built only from allowed fields and question numbers either computes or rejects, never raises.
